The Switchboard

Your prompt is a phone call. Pi is the operator routing it through five junction boxes before the AI ever picks up.

Pi is not the AI

You type "summarize this file" and the AI responds. Feels like one thing talking to you. It is not.

Pi is a CLI that wraps an AI. It runs in your terminal, takes your text, and talks to a language model on your behalf. The model lives somewhere else (OpenAI, Anthropic). Pi lives on your laptop.

The Model just predicts text

Think of an old telephone switchboard operator: you tell them "connect me to my aunt in Cleveland" and they physically plug wires into the right sockets. Pi is the operator. The model is your aunt. Most things that go wrong, go wrong in the wires — not at your aunt's house.

💡
The thing to remember

The model never touches your computer. It only writes text. Every file change, every command, every API call is pi running a tool on the model's behalf. If something happened on your machine, pi did it — not the AI.

The journey of one prompt

You type summarize this README and hit Enter. Before the model sees a single word, your message passes through five distinct stages inside pi.

1
Input capture

Interactive mode reads what you typed in the little editor at the bottom of the screen. Print mode reads it from the command-line arguments you ran pi with.

2
Preflight

Pi peeks at your message before sending it. Did you type a slash command like /clear? Did you reference a skill? Is a model even configured? These checks happen here.

3
System prompt assembly

Pi mixes a hidden bundle of text: base instructions, tool descriptions, any active skills, and a sketch of your project. This becomes the system prompt — the briefing the model reads before answering you.

4
LLM call

Pi packages your message plus the system prompt and ships it over the network to the model's API. This is the only stage where your text leaves your laptop.

5
The turn loop

The model replies. If it asked to run a tool, pi runs it, sends the result back, and the model speaks again. This loop continues until the model says "I am done" — which might be one round, or twenty.

The class that orchestrates all of this is called AgentSession. Here is how the pi codebase describes it, in its own words.

CODE 
/**
 * AgentSession - Core abstraction for agent lifecycle and session management.
 *
 * This class is shared between all run modes (interactive, print, rpc).
 * It encapsulates:
 * - Agent state access
 * - Event subscription with automatic session persistence
 * - Model and thinking level management
 * - Compaction (manual and auto)
 * - Bash execution
 * - Session switching and branching
 *
 * Modes use this class and add their own I/O layer on top.
 */
PLAIN ENGLISH

This is the brain that sits between your keyboard and the AI.

It works the same way whether you launched pi to chat, to run one quick prompt, or to be controlled by another program.

It tracks the conversation state.

It listens for things happening and saves the session to disk so nothing is lost.

It picks which model to call and how hard it should think.

It compresses old conversation when memory fills up.

It runs shell commands when the model asks.

It can split a conversation off into a side-branch and switch back.

In short: every chapter of this course is one bullet from this list.

The turn loop (the most important idea in this course)

The model is not a one-shot oracle. It does not read your prompt and produce one final answer. It works in turns.

Each turn, the model says either "here is some text for the user" or "please run this tool for me." Pi handles the tool call, hands the result back, and the model takes another turn. The cycle repeats until the model decides it has nothing left to ask for.

Why this matters when things go wrong

When pi "gets stuck" running the same command over and over, it is not a glitch — it is the turn loop. The model keeps asking for the same tool because the result keeps not satisfying it. Knowing this, you can break the loop with a fresh message instead of waiting helplessly.

The four tools the model can actually use

The model can ONLY affect the world through tools. Pi ships four built-in ones. That is the entire vocabulary the AI has for touching your computer.

📖
read

Open a file and return its contents.

✍️
write

Create a new file or overwrite an existing one.

✂️
edit

Change a specific chunk of a file without rewriting the whole thing.

💻
bash

Run a shell command — anything you could type in your terminal.

Plus a few helpers like find, grep, and ls. But what is a tool, technically? It is a name, a description, and a schema for its arguments. Here is the real one for bash.

CODE 
const bashSchema = Type.Object({
    command: Type.String({ description: "Bash command to execute" }),
    timeout: Type.Optional(Type.Number({ description: "Timeout in seconds (optional, no default timeout)" })),
});
PLAIN ENGLISH

When the model wants to run a shell command, this is the shape of the request it has to send.

It must include a piece of text called command — the actual command line, like ls -la. The description tells the model what this field is for.

It can optionally include a number called timeout — how many seconds to wait before giving up. If the model leaves it out, pi waits forever.

End of the recipe. If the model sends anything that does not match this shape, pi rejects it before running anything.

That is the entire grammar of a tool: a name (bash), a description (what it does), and a schema (what fields the call must contain). The model reads this in the system prompt and then crafts requests that match.

02

Meet the Cast

Pi is a film crew, not a one-person show. Time to learn the names on the call sheet.

Why a crew, not a hero?

When pi answers your prompt it looks like one thing happened. Under the hood, seven different pieces of code took a turn. Each one has a single job.

Think of an airport. One plane lands and rolls to the gate, but a small army made that happen: check-in, security, baggage, fueling, air-traffic control. Nobody tries to do all five. If the baggage belt jams, you fix the belt — you don’t rebuild the runway.

✈

One job each

Air-traffic control routes planes. Baggage moves bags. Nobody multitasks. The work is cleaner because the role is narrow.

🛠

Swap without panic

Fuel truck breaks? Bring another fuel truck. You don’t need to ground every flight or retrain the pilots.

🔍

Precise bug reports

“Bag never arrived” points at one team. “The airport is broken” points at nobody.

💡
The big idea: separation of concerns

Separation of concerns is one of the most important ideas in software. When each component owns one job, you can swap, debug, or scale any of them without disturbing the rest. It is why pi has three run modes built from one core.

The seven actors on set

Here is the whole call sheet. Read it once and you will have the vocabulary to talk about pi like an engineer.

🎬

Coordinates everything: takes your prompt, calls the model, runs tools, writes results to disk, decides when to compact the history.

📱

A lower-level library that actually talks to the language model API. AgentSession wraps it.

👋
Tools — the hands

Functions the model can ask to run: read, write, edit, bash, plus a handful of search helpers. The model itself never touches your disk — tools do.

📝

Writes every message, tool call, and result to a .jsonl file on disk so the conversation survives a crash and can be replayed.

👜

User-installed plug-ins that can register new tools, listen for events, add slash commands, or replace built-in behavior.

📚

Markdown files that teach the model how to do specific tasks on demand. Think of them as scripts the director can hand the lead actor mid-scene.

🎥
Modes — the three cameras

Same engine, different framing: interactive (the live TUI in your terminal), print (one-shot, scripting), and RPC (machine-to-machine for IDE plugins).

AgentSession: the director, up close

If you only remember one name from this module, make it AgentSession. It is the orchestrator — the one piece of code that the other six all answer to. The comment at the top of the file says exactly what it owns.

CODE 
/**
 * AgentSession - Core abstraction for agent lifecycle and session management.
 *
 * This class is shared between all run modes (interactive, print, rpc).
 * It encapsulates:
 * - Agent state access
 * - Event subscription with automatic session persistence
 * - Model and thinking level management
 * - Compaction (manual and auto)
 * - Bash execution
 * - Session switching and branching
 *
 * Modes use this class and add their own I/O layer on top.
 */
PLAIN ENGLISH

AgentSession is the brain of one conversation. Every prompt you send lives inside one.

Shared between all run modes. Whether you use pi in your terminal, in a script, or via an IDE plugin, the same class runs the show.

Agent state access. Knows what has been said so far — the running transcript.

Event subscription with automatic session persistence. Listens for things that happen and writes them to disk so nothing is lost.

Model and thinking level management. Knows which model to call and how hard to make it think.

Compaction (manual and auto). Decides when to summarize the chat to save space when the history gets long.

Bash execution. Runs shell commands on your behalf when the model asks for them.

Session switching and branching. Lets you jump between conversations or fork one to try a different path.

Modes add their own I/O layer on top. The three ways to run pi all share this brain; only the screen they draw on differs.

Read that last line twice. It is the whole shape of pi in one sentence: one brain, three faces.

Tools: The Model's Hands

The model speaks. Tools are how speech becomes action.

The DJ behind the glass

Picture a radio DJ inside a soundproof booth. They can talk all day, but if they want to play a song, they press one of the labeled buttons on the panel in front of them. They cannot reach through the glass to spin a record themselves.

The model is the DJ. Tools are the buttons. The panel is the list of tools pi tells the model about at the start of every session.

The model is on the wrong side of the glass.

It speaks, but it doesn't act. If you want it to do something new — call an API, deploy a service, query a database — you (or an extension) must install a tool that does that. Then the model can press the button.

Anatomy of a tool

A tool is three things bundled together: a name the model uses to call it, a description the model reads to decide whether to use it, and a schema that says what arguments are allowed.

Here is the smallest possible complete tool in pi — a friendly “hello” greeter. Every other tool in the system, including the powerful ones like bash, has the same shape underneath.

CODE 
/**
 * Hello Tool - Minimal custom tool example
 */

import { Type } from "@earendil-works/pi-ai";
import { defineTool, type ExtensionAPI } from "@earendil-works/pi-coding-agent";

const helloTool = defineTool({
    name: "hello",
    label: "Hello",
    description: "A simple greeting tool",
    parameters: Type.Object({
        name: Type.String({ description: "Name to greet" }),
    }),

    async execute(_toolCallId, params, _signal, _onUpdate, _ctx) {
        return {
            content: [{ type: "text", text: `Hello, ${params.name}!` }],
            details: { greeted: params.name },
        };
    },
});

export default function (pi: ExtensionAPI) {
    pi.registerTool(helloTool);
}
PLAIN ENGLISH

Comment block. Just a note for humans saying “this file defines a hello tool.”

Pull in Type, the helper used to describe what arguments look like.

Pull in defineTool (the tool-builder) and the ExtensionAPI type from pi.

Build a tool. The thing inside the parens is the tool's full definition.

The model will refer to this tool by the word hello.

How the tool's name shows up in the pretty UI when it runs.

What the model reads to decide whether to use this tool. The model can only call tools it knows about, and it reads the description to know what each one does.

The shape of arguments this tool expects — here, one string called name. This is the tool's schema.

The actual code that runs when the model presses this button. params holds the arguments the model sent.

What the tool sends back. content goes to the model so it can keep working; details is extra info the UI might show.

Closing the return value, closing execute, closing the tool definition.

Tell pi about this tool so it shows up on the panel and can be called.

What the model actually sees

When pi tells the model about the bash tool, here is the exact shape it sends. The model has to produce JSON matching this shape — anything else gets rejected.

CODE 
const bashSchema = Type.Object({
    command: Type.String({ description: "Bash command to execute" }),
    timeout: Type.Optional(Type.Number({ description: "Timeout in seconds (optional, no default timeout)" })),
});
PLAIN ENGLISH

Describe the shape of arguments. Type.Object means “expect a JSON object with these fields.”

Field one: a string called command. Required. This is the shell command the model wants pi to run.

Field two: an optional number called timeout. If the model thinks the command might hang, it can set a cap in seconds.

End of schema. From here on, the model knows: “to press the bash button, send a JSON object with command (and maybe timeout).”

WHAT THE MODEL EMITS
{
  "tool": "bash",
  "args": {
    "command": "npm test"
  }
}
→
WHAT PI DOES
  1. Check the JSON against bashSchema.
  2. If valid, run the bash tool with command = "npm test".
  3. Capture stdout/stderr; stream lines back.
  4. Hand the final result to the model as a tool result.

Spot the bug: what makes this tool call invalid?

1 {
2 "tool": "bash",
3 "args": { "cmd": "npm test", "timeout": 30 }
4 }

The wrapper: a tiny adapter

Tools are written one way (rich, with full context like “what session am I in?”), but agent-core wants a simpler shape. The wrapToolDefinition function is the adapter between the two — like an HDMI-to-USB-C dongle.

CODE 
export function wrapToolDefinition<TDetails>(
    definition: ToolDefinition<any, TDetails>,
    ctxFactory?: () => ExtensionContext,
): AgentTool<any, TDetails> {
    return {
        name: definition.name,
        execute: (toolCallId, params, signal, onUpdate) =>
            definition.execute(toolCallId, params, signal, onUpdate, ctxFactory?.() as ExtensionContext),
    };
}
PLAIN ENGLISH

Define a function called wrapToolDefinition. It is the dongle.

It takes a tool definition — the fancy shape with five execute arguments.

It also takes an optional ctxFactory — a way to look up the current extension context when the tool actually runs.

It returns an AgentTool — the simpler shape agent-core wants.

Build the simpler shape…

…keeping the original name so the model still recognises it…

…and providing an execute that takes only four arguments.

When agent-core calls execute, the wrapper calls the real execute and quietly injects the fifth argument (the context) by asking ctxFactory.

Close the returned object.

End of function.

🧩
Why this matters for extensions

Module 6 covers extensions, which add new buttons to the panel. The wrapper is the reason an extension tool can know “which session am I in?” without every tool author having to wire that up by hand.

04

Memory as a Tree

Every conversation is a choose-your-own-adventure book — with all the branches still bound inside.

The book is on the shelf

Close your terminal. Walk away. Come back tomorrow. Type pi -c. Every message is exactly where you left it — because the conversation was never really “in” the terminal. It was on disk the whole time.

Pi writes one JSONL file per session. Every user message, every model reply, every tool call gets appended as a single line. The file is the book. Your conversation is what is written in it.

WHERE PI STORES YOUR SESSION
~/.pi/agent/sessions/-home-user-myproject/2025-05-16_e3a1b8c9.jsonl
pi’s home — where every session for every project lives
folder you ran pi in — the slashes get flattened to dashes
date + uuid — one file per session, never reused
📚
Pi sessions are not chat logs.

They look like chat logs — but underneath, they are trees. That single fact is what makes /tree, /fork, and undo possible. The rest of this module unpacks how.

The shape of one entry

Every line in the file describes one moment in the conversation. They all share the same four fields, plus a message field when the entry is something somebody said.

Here is the shape, taken from pi’s session manager. SessionEntryBase is the common spine; SessionMessageEntry is the most common flavor.

CODE 
export interface SessionEntryBase {
    type: string;
    id: string;
    parentId: string | null;
    timestamp: string;
}

export interface SessionMessageEntry extends SessionEntryBase {
    type: "message";
    message: AgentMessage;
}
PLAIN ENGLISH

Every entry in the file has at least these four fields…

type — what kind of entry this is. "message" is the most common; others include "compaction" and "branch_summary".

id — a short unique label for this entry, so other entries can point back to it.

parentId — the id of the entry that came right before this one in the chain. If null, this is the first entry in the session.

timestamp — when this entry was written.

End of the common shape.

A more specific kind of entry: one that contains an actual conversation message…

…its type is literally the word "message".

…and it carries a message field with the actual user / assistant / tool content.

End of definition.

🔗
parentId is the whole trick.

Each entry points to the one before it. Walk the parent pointers backward and you reconstruct the conversation. Because any entry can claim any earlier entry as its parent, two entries can share a parent — and that is how a straight line turns into a tree.

Same story, three views

Here are three real lines from a session file: the header, a user message, and the model’s reply. Same conversation, three ways to look at it — flip the tabs below.

When you rewind and ask something different, the old answer doesn’t get deleted — it just becomes a sibling. Two children, one parent. Welcome to the tree.

From a line to a tree

A linked list says “each item points to one next item.” A tree says “each item can have many next items, but only one previous.” That tiny change is the entire feature.

Here is what a session file looks like once you’ve rewound and tried something different. Same file, two paths.

CODE — THE BRANCH DIAGRAM 
[user] ── [assistant] ── [user] ── [assistant] ─┬─ [user] ← current leaf
                                                 │
                                                 └─ [branch_summary] ── [user] ← alternate branch
PLAIN ENGLISH

The main path: four entries in a row — user, model, user, model — then a fork where two different next-messages share the same parent.

The vertical line is just ASCII for “both of these point up to the same entry.”

The other branch starts with a branch_summary — a tiny note pi writes when you jump back, recording where the detour begins. Then the alternate user message. Both leaves live in the same file forever.

Walking the tree to build context

When pi calls the model, it does not send the whole file. It walks from the current leaf back to the root, collecting ancestors in order. That ordered list is the conversation the model sees — nothing else.

1

Find the current leaf (the entry you’re standing on).

→
2

Follow parentId upward, one hop at a time.

→
3

Stop when parentId is null — that’s the root.

→
4

Reverse the list. Hand it to the model as “the conversation.”

💡
A tree is just a linked list where each node can have multiple children.

That single change — letting one parent have many kids — gives you branching, versioning, and undo for free. Git uses the same idea to track code. Your browser’s back button uses it to track pages. Pi uses it to track conversations.

Three ways to branch

Pi exposes the tree through three commands. Pick the one that matches what you’re trying to do.

🌳

/tree

Navigate the tree in place. Jump to any earlier entry and continue from there. The original branch isn’t deleted — it’s set aside.

USE WHEN

You went down a wrong path and want to undo the last few turns without losing earlier work.

🔱

/fork

Copy the path from the start up to a chosen point into a brand-new session file. Two files, two futures.

USE WHEN

You want to share a session, or try something destructive without touching the original.

When Context Runs Dry

A reporter's notebook only has so many pages. Here is how pi tears out the old ones without losing the story.

The reporter with a finite notebook

Imagine a field reporter on a two-week assignment with one fixed-size notebook — say 200 pages. Around page 180 they hit a wall: the notebook is almost full, but they still need everything they wrote down.

So they do something clever. They tear out the first 150 pages, sit down for ten minutes, and replace them with one page of bullet-pointed highlights. The most recent 50 pages of detailed notes stay untouched. New entries continue from the summary page forward. The notebook keeps working.

This is exactly what pi does to the model's memory. Every language model has a context window — a hard limit on how much text it can look at in a single call, measured in tokens. Sonnet's notebook is around 200,000 tokens long. Smaller models have smaller notebooks.

⚠
The original messages are not deleted from the file.

They are just hidden from the model. You can always scroll back through /tree to see what was said before compaction. Compaction is about what the model sees, not what is on disk.

Two triggers, two responses

Pi runs compaction in two situations — one before the wall, one after. Think of it as a careful reporter who tries to summarise before the notebook fills up, but who also knows how to recover if they accidentally write past the last page.

⏱

Threshold compaction

Proactive. After each turn, pi checks token usage. If we are within the safety reserve of the window, compact before the next call so we never crash.

TRIGGERcontext > window − 16K
🔩

Overflow recovery

Reactive. If the model returns an “out of context” error anyway, pi removes the error, compacts the history, and retries the request automatically.

TRIGGERmodel returns overflow error

The proactive check is one of the smallest, sharpest pieces of code in the whole compaction system. Three lines.

CODE 
export function shouldCompact(contextTokens: number, contextWindow: number, settings: CompactionSettings): boolean {
    if (!settings.enabled) return false;
    return contextTokens > contextWindow - settings.reserveTokens;
}
PLAIN ENGLISH

A simple function that answers yes or no: do we need to compact right now?

If the user turned auto-compaction off in their settings, never trigger it.

Otherwise, return true whenever the tokens we are using have crossed past the limit minus a safety reserve. The reserve (default 16,000 tokens) leaves room for the model's reply.

End of function. The whole decision fits in three lines because pi only needs to ask one question.

What compaction actually does

When shouldCompact says yes, pi runs a five-step ritual. The goal: replace a long stretch of old messages with one compact entry that the model can still reason from.

1
Find a cut point

Walk backward from the newest message until about 20,000 tokens of recent context are kept. Everything older than the cut will be summarised.

2
Bundle the older messages

Everything before the cut gets grouped into one chunk — the pages pi is about to tear out.

3
Ask the model to summarise

Pi makes a separate LLM call: “summarise this conversation, preserving key decisions and file changes.”

4
Track which files were touched

Separately, pi scans the compacted messages for tool calls and builds two lists: files that were read, and files that were modified.

5
Write a CompactionEntry and replace the past

Pi stores the summary plus the file lists as a single entry in the session tree. Next turn the model sees: system prompt + summary entry + last 20,000 tokens. Crisis averted.

The file-tracking part has its own little shape. When pi compacts, it does not just produce prose — it also remembers exactly which files were touched in the compacted section.

CODE 
export interface CompactionDetails {
    readFiles: string[];
    modifiedFiles: string[];
}
PLAIN ENGLISH

Declare a shape called CompactionDetails. This is the structured side-car that travels with the prose summary.

readFiles: a list of file paths the agent looked at in the chunk being summarised.

modifiedFiles: a list of file paths the agent actually changed.

End of shape. Now even after the detailed messages are gone, the model — and you — can see what was worked on.

The whole point is to throw information away so the conversation can continue. The model will sometimes lose a detail — that is the trade. It is also why you can manually trigger compaction with custom instructions like /compact "preserve the API contract" to keep what matters to you.

Pi is a power strip. The interesting stuff is what you plug in.

The minimalist’s bet

Think of pi as a power strip with empty outlets. The strip by itself does almost nothing — a few minimal tools, a basic UI, the turn loop. The interesting power comes from what you plug in.

Other AI coding tools ship as full appliances: plan mode built in, sub-agents built in, MCP built in. Pi has none of these by default. That is the bet.

README 
Pi is aggressively extensible so it doesn’t have to dictate your workflow.

PLAIN ENGLISH

Aggressively extensible — pi does not pick a workflow for you. It picks a kit.

Third-party packages — the npm-style ecosystem. Anyone can publish, you install what you want.

💡
Why ship a kit instead of a finished product?

Because every team’s workflow is different, and a baked-in feature is one you can never fully change. A small core plus open outlets beats a big core with locked switches.

Three kinds of plug

Pi exposes three official outlets. Each one fits a different shape of customization. Pick the smallest one that solves the problem.

📝

Skills

Markdown files in ~/.pi/agent/skills/. The model reads them on demand when relevant. Best for instructions, conventions, how-tos — “here is how our team writes PRs.”

📋

Prompt Templates

Markdown with placeholders in ~/.pi/agent/prompts/. Type /templatename in chat and it expands. Best for repeated prompts: /review, /explain, /refactor.

⚡

Extensions

TypeScript code that pi loads at startup. Best for anything dynamic — new tools, event hooks, integrations, custom UI.

📝
Choose a skill when…

You want pi to know something static. Conventions. Style guides. “Always check this file before touching the database.”

📋
Choose a template when…

You keep typing the same prompt. Turn it into /review security or /draft-pr with a saved file and an argument slot.

⚡
Choose an extension when…

You need code to run — a new tool, a confirmation popup, a Slack ping, a git checkpoint. Anything dynamic.

A real extension, end to end

Here is a complete, working extension from examples/extensions/permission-gate.ts. Thirty lines. It blocks rm -rf, sudo, and chmod 777 until you confirm in the TUI.

permission-gate.ts 
/**
 * Permission Gate Extension
 *
 * Prompts for confirmation before running potentially dangerous bash commands.
 * Patterns checked: rm -rf, sudo, chmod/chown 777
 */

import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";

export default function (pi: ExtensionAPI) {
    const dangerousPatterns = [/\brm\s+(-rf?|--recursive)/i, /\bsudo\b/i, /\b(chmod|chown)\b.*777/i];

    pi.on("tool_call", async (event, ctx) => {
        if (event.toolName !== "bash") return undefined;

        const command = event.input.command as string;
        const isDangerous = dangerousPatterns.some((p) => p.test(command));

        if (isDangerous) {
            if (!ctx.hasUI) {
                // In non-interactive mode, block by default
                return { block: true, reason: "Dangerous command blocked (no UI for confirmation)" };
            }

            const choice = await ctx.ui.select(`⚠️ Dangerous command:\n\n  ${command}\n\nAllow?`, ["Yes", "No"]);

            if (choice !== "Yes") {
                return { block: true, reason: "Blocked by user" };
            }
        }

        return undefined;
    });
}
PLAIN ENGLISH

Doc comment. Tells humans what this file is for.

Pull in the ExtensionAPI type so the editor can autocomplete what pi gives us.

Every extension is a function pi calls at startup, handing it the extension API as pi.

A list of three regular expressions — the patterns we treat as dangerous.

Subscribe to the tool_call event. Pi will run this function every time the model wants to call any tool.

Only care about bash calls. For everything else, return undefined — pi-speak for “no opinion, let it through.”

Grab the command string the model wants to run.

Check it against every pattern. If any match, it is dangerous.

If we are running headless (no UI), play it safe and block.

Otherwise, pop up a TUI dialog asking the user to allow or deny.

If they said anything other than Yes, return a block decision. Pi will not run the tool and will tell the model why.

All clear — return undefined and let the command through.

Notice what is not here. No mention of pi’s internals. No fork. No monkey-patching. Just one event subscription and a return value. That is the whole API.

How extensions stay out of each other’s way

Pi can run many extensions at once. If one of them throws an error, you do not want it dragging the whole session down. Pi’s event bus is the safety layer that keeps extensions isolated.

Think of it as a postal sorting facility. Many recipients, one stream of letters, each recipient only opens their own. If one recipient drops their letter and screams, the next recipient still gets theirs.

event-bus.ts 
on: (channel, handler) => {
    const safeHandler = async (data: unknown) => {
        try { await handler(data); }
        catch (err) { console.error(`Event handler error (${channel}):`, err); }
    };
    emitter.on(channel, safeHandler);
    return () => emitter.off(channel, safeHandler);
},
PLAIN ENGLISH

on is the function extensions call to subscribe. It takes a channel name and a handler function.

Pi does not pass your handler straight to the emitter. It wraps it in safeHandler first.

The whole point: try/catch. Run your handler. If it explodes, catch the error.

When it explodes, log it and keep going. One bad extension cannot crash pi.

Register the safe wrapper with the underlying emitter, not your original.

Hand back a function that unsubscribes you cleanly. Plug in — and unplug.

A tiny custom tool

Permission gates intercept existing tools. The other half of extension power is adding new tools the model can press. Same tool shape from module 3 — just installed at runtime instead of baked in.

hello.ts 
const helloTool = defineTool({
    name: "hello",
    label: "Hello",
    description: "A simple greeting tool",
    parameters: Type.Object({
        name: Type.String({ description: "Name to greet" }),
    }),

    async execute(_toolCallId, params, _signal, _onUpdate, _ctx) {
        return {
            content: [{ type: "text", text: `Hello, ${params.name}!` }],
            details: { greeted: params.name },
        };
    },
});

export default function (pi: ExtensionAPI) {
    pi.registerTool(helloTool);
}
PLAIN ENGLISH

Define a tool. defineTool is the same builder pi’s built-in tools use.

The model calls it by name. hello is what shows up in the tool list.

Human-readable label, mostly for the UI.

The description the model reads to decide when to use this tool.

The schema — what arguments the model is allowed to pass.

One required argument: a name string.

The function that actually runs when the model presses the button.

Return a result object. Content is what the model sees next turn.

Details is structured metadata pi can log or display in the UI.

The install line. Same extension shape: a function pi calls at startup. Inside, call registerTool and the model now has a new button.

🔗
Same shape, different source.

The bash tool, the read tool, the hello tool above — they all use this same defineTool structure. The only difference is whether they ship in pi’s tarball or live in a file in ~/.pi/agent/extensions/. The model cannot tell them apart, and it does not need to.
